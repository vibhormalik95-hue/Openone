# Hivemind Scale: executed proof and precise limits

The supplied proof demonstrates shared, versioned project memory across three separately authenticated scripted agents using both the classic MCP lifecycle and the 2026 tool core. It does not establish universal host autonomy, live Claude/ChatGPT/Cursor interoperability, or enterprise product parity. The evidence is a signed execution record of the bounded workflow below.

## What actually ran

`tests/investor_proof_harness.py` creates a disposable synthetic two-tenant fixture through an administrator connection, then runs the production application under Uvicorn on a private loopback TCP port. An actual HTTPX client sends bearer-authenticated JSON-RPC requests through the production HTTP router, token verifier, tool descriptors, Pydantic validation, ledger engine, psycopg driver and SQL functions. Three different project-scoped keys represent Agent 1, Agent 2 and Agent 3. Client names are scripted labels; possession of those keys is the authenticated identity.

The completed local execution used PostgreSQL **17.5** compiled to WebAssembly with pgvector **0.8.0**, exposed through the PGlite PostgreSQL wire socket. This engine has **one shared database session**. The harness explicitly lowers that session to `hivemind_app`, then checks `current_user = hivemind_app`, `rolsuper = false` and `rolbypassrls = false`. It does not substitute a fake SQL engine or an administrator for application operations. This is still not equivalent to native PostgreSQL login authentication, independent backend sessions, connection-pool isolation or real concurrency. The native quickstart provides a separate disposable PostgreSQL deployment with a real application-role login; that path remains unexecuted in this workspace.

The test makes **15 actual HTTP invocations** and passes **7 grouped workflow assertions**. Exact assertion statements, requests, responses, UTC timestamps, source hashes and SQL receipts are embedded in `evidence/investor-proof.json`; the process output is `evidence/investor-execution.log`.

| Step | Transport and credentials | Verified behavior |
|---|---|---|
| Initialize two older callers | MCP `2025-11-25`, two independent keys | `initialize` succeeds and supplies `instructions` |
| Discover the modern server | MCP `2026-07-28`, third key | `server/discover` succeeds without initialization |
| List tools through both paths | Classic and modern | Exactly `sync_context` and `manage_ledger` are returned |

Agent 2’s “10 minutes later” has an explicitly recorded logical offset of **600 seconds**. The test does not wait ten real minutes or change database timestamps. All timestamps are actual execution UTC. The test models a fresh caller with an empty conversation by supplying only a recall query and the explicit `no_new_context` checkpoint; the server does not receive the earlier caller’s conversation.

## Exact state and deterministic schema

Version 1 is preserved byte-for-byte as the JSON string:

```text
DB must use PostgreSQL 17 with strict serializable isolation; JWT secrets rotate every 12 hours
```

Version 2 is:

```text
DB must use PostgreSQL 17 with strict serializable isolation; JWT secrets rotate every 6 hours
```

Both underlying immutable rows retain their declared `accepted` state. The security-invoker lifecycle view derives version 1 as `superseded` and version 2 as `active`. That distinction avoids rewriting historical records.

Agent 2's API schema is generated by a deliberately strict fixture compiler. It recognizes the exact constraint grammar, extracts PostgreSQL major version and rotation hours, and fails closed for an unrecognized statement. Its OpenAPI response schema uses constants `17`, `SERIALIZABLE` and `43200` seconds. The verifier regenerates that schema from the recorded tool packet and compares the full result. This proves the selected structured response can ground a deterministic consumer; it is not a test of a live model's reasoning, hallucination rate or automatic tool choice.

The embedding provider is a deterministic hash-vector fixture. It exercises nonblocking provider invocation and vector parameter transport without spending a real API key or representing a real embedding model. Accepted claims queue durable embedding jobs; this workflow does not drain those jobs or certify semantic model quality. Exact authoritative recall remains available independently of completed embeddings. Separate SQL tests cover vector retrieval and outbox mechanics.

## Independent cryptographic verification

The fixture creates exactly **four durable audit-chain entries**: two accepted-write events and two immutable ledger revisions. Identical retries add no event or revision. Every entry exports three canonical preimages:

1. `canonical_source`: Python SHA-256 must equal `source_content_digest`.
2. `canonical_row`: Python SHA-256 must equal the row digest inside the commitment.
3. `canonical_commitment`: Python SHA-256 must equal `chain_hash`.

The verifier checks the commitment's domain, tenant, project, sequence, previous hash, entry type, source identity and content digest against the exposed row and surrounding bundle. It checks source timestamps, links the source preimage to the event payload or revision fields, verifies consecutive hash links, and requires the final checkpoint to match the final row with `has_more = false`. Every SQL tool receipt is similarly checked against its canonical receipt, actual authenticated agent key, event identity and returned audit checkpoint. SQL receipt digests are unsigned database commitments; the separate export signature covers the complete HTTP evidence.

HTTP invocation records form a second SHA-256 chain. Each contains the actual request/response, protocol, nonsecret credential label, real start/end timestamps and logical time offset. Authorization values and raw keys are deliberately omitted. The complete canonical evidence bundle is signed by an ephemeral Ed25519 key; only the public key and signature are exported. The private key is discarded.

**Trust boundary:** a self-contained public key proves internal integrity but does not authenticate its own origin. Someone who can replace the whole file can replace its key and sign a different file. Publish the bundle digest or public-key fingerprint through an independently trusted channel, then supply it to the verifier. The harness tests that an altered invocation fails verification and that re-signing with a substituted key fails when the original fingerprint is pinned. It does not claim external timestamping, vendor attestation, completeness of unsent conversation history, or cryptographic tenant encryption.

## Bounded mathematical verification

`tests/verify_ledger_model.py` exhaustively explores an independent finite reconciliation model: **one entity, two values, two tenants, three idempotency keys and at most three successful events**. The completed run visits **2,029 reachable states** and checks **26,424 transitions**, plus both serial orders of two conflicting same-version writers.

The checked properties are immutable history and event prefixes; no change on rejected requests or identical retries; tenant isolation; contiguous versions; optimistic compare-and-swap; atomic event/revision creation; preservation of accepted authority by tentative proposals; duplicate resolution without a new revision; and retraction removing active state. For example, a rejected transition requires `H′ = H`, while every successful new revision requires `expected_version = |H|` and `|H′| = |H| + 1`. Two different writers that both observed version zero produce one winner and one conflict in either serialized order.

This is a complete exploration of the declared **abstract finite model**. It is not a machine-checked refinement proof connecting all SQL/Python executions to that model, nor a proof of arbitrary cluster schedules, liveness, availability or LLM behavior. The HTTP trace provides separate concrete implementation evidence for the selected workflow. The exact model output and its source hash are in `evidence/ledger-model-proof.json`.

## Reproduce and qualify further

Portable execution:

```bash
npm ci --prefix tests --ignore-scripts
HIVEMIND_TEST_PYTHON=python node tests/pglite-investor.mjs
PYTHONPATH=src python tests/investor_proof_harness.py --verify evidence/investor-proof.json
python tests/verify_ledger_model.py --output evidence/ledger-model-proof.json
```

For the complete scripted setup, use `./quickstart.sh --portable-proof`. Use the native quickstart on a Docker-capable machine to test native PostgreSQL and its separately collected concurrency cases. The direct harness also accepts `INVESTOR_ADMIN_DATABASE_URL` and `INVESTOR_APP_DATABASE_URL`; they must point to a disposable, fully migrated test database. The native application URL must authenticate as `hivemind_app`. Synthetic audit rows remain immutable until that disposable database is destroyed.

Release qualification still requires real hosted-client OAuth and approval behavior, Claude/ChatGPT/Cursor acceptance, native multi-session concurrency, TLS/proxy streaming, real provider extraction/embedding behavior, Stripe webhook/onboarding integration and cloud deployment. No remote protocol can prove capture of conversation a host never sends. A server-side context challenge prevents this service from falsely acknowledging an empty capture; the host still controls whether it supplies the missing context, retries, displays an action or invokes the tool at all.
