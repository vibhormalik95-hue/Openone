# Headless MCP core: execution decisions and verified implementation

Research date: 10 September 2026. This is a deployable reference implementation with local tests; it is not evidence that a live service, paid subscription, or every native client has passed acceptance.

## Architecture decision

Use Python 3.12, FastMCP 3.4.7's slim server distribution, FastAPI only for operational/billing endpoints, psycopg 3 asynchronous connections, PostgreSQL 17, pgvector 0.8.x, and a PostgreSQL lease worker. Users retain their existing native model interfaces. Astro supplies three small commercial pages: landing, onboarding, and account/key management. No chat interface, model router, hosted editor, or custom conversation store is introduced.

The public MCP surface is exactly two tools. Runtime tenant identity comes from a verified credential, never from a caller-controlled tenant parameter. Both tools require an explicit project UUID. Semantic embeddings are generated by the service's restricted OpenAI project key. Upstream native Claude/ChatGPT/Cursor usage is billed and governed by the user's existing provider account.

FastMCP's HTTP application supports custom paths, Streamable HTTP, stateless deployments, and ASGI integration. A mounted application's lifespan must be entered explicitly to initialize its session manager. The implementation mounts the transport at the root ASGI router after the non-MCP routes, making the endpoint exactly `/mcp/v1` without a redirect or doubled prefix. [FastMCP HTTP deployment](https://gofastmcp.com/deployment/http)

## Authentication and client compatibility

The beta credential format is `hvm_` followed by a cryptographically random URL-safe secret. The database stores SHA-256 digests, not plaintext credentials. With 256-bit randomly generated secrets, a slow password KDF is unnecessary; passwords would require a different design. Tokens are passed in `Authorization: Bearer ...` on every HTTP request. `/mcp/v1?token=...` and `?access_token=...` are deliberately rejected. Query-string bearer tokens violate the MCP authorization specification and leak through URL handling. [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

The API-key verifier authenticates the HTTP request, then each actual tool transaction revalidates the digest and binds its key ID using the database authentication function. This closes the gap between initialization and a later tool call, and between pooled connection borrowers. Project permissions, key revocation, expiration, subscription entitlement, and member restrictions remain database decisions. A session ID is not an identity. Raw SQL errors never become tool output.

API-key mode is suitable only for clients that can supply a custom Authorization header. It is not a complete MCP OAuth authorization server. Optional OAuth uses the managed-provider adapter in `oauth.py` and its own runbook. Discovery metadata, issuer/audience verification, PKCE, exact redirect registrations, explicit paid-account binding, encrypted distributed token storage, and end-to-end native-client tests are launch gates. Hosted-client support must not be inferred from a successful local bearer test.

Legacy HTTP+SSE is a separate, explicitly enabled `/legacy/sse` endpoint with `/legacy/messages/` POST handling. It is not a protocol switch at `/mcp/v1`. The default modern endpoint itself returns SSE-formatted Streamable HTTP responses. Legacy is limited to API-key mode; startup rejects combining legacy with OAuth to avoid shared auth-provider resource-path mutation. Enable legacy only for a verified client that needs it, with one process/replica or a correctly designed session-routing layer. The MCP transport specification distinguishes the legacy transport and prescribes how clients can detect/fall back. [MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

## Tool contract and correctness

`schemas/commit_memory.json` and `schemas/recall_memory.json` contain complete JSON Schemas. MCP tool arguments are shaped as `{ "request": { ... } }`. Pydantic forbids unknown fields and scalar coercion, validates UUIDs, limits array sizes and content lengths, rejects empty commits and duplicate constraint keys, and bounds metadata/constraint JSON. Client-provided tenant IDs are rejected.

`commit_memory` captures already structured decisions, tasks, state, notes, and exact constraint changes. It does not secretly invoke a model, read other clients' chat histories, or infer memory from a webhook. The native assistant performs extraction using `prompts/project-memory.md`; its permission settings still apply. Database commit and queue insertion are atomic. A success acknowledges durable SQL storage, while semantic indexing may remain queued.

Idempotency is scoped to tenant/project/key. A canonical JSONB payload digest detects a changed replay and rejects it; a same-payload replay returns the original event without applying mutations or charging a second commit. Constraint updates require the latest ledger version, including a previously superseded version. Recall exposes the latest versions in constraint_versions even for inactive keys; the project allows at most 128 distinct historical constraint keys to keep this map bounded. Recall returns a separate constraint_versions map for every known key, including inactive keys, so a new client can reactivate a constraint safely. The ledger permits at most 128 distinct keys per project; an excess commit fails atomically. A project-level lock serializes concurrent commits; the losing stale update receives a version conflict. Semantic deduplication is deliberately conservative: identical trimmed text, kind, and metadata are deduplicated, while merely similar statements remain distinct evidence. Automated approximate merging could erase meaningful contradictions.

`recall_memory` checks project access and remaining monthly allowance before spending on an embedding; final retrieval charges its quota atomically. This read-only preflight cannot reserve capacity against every racing replica, so at most the admitted concurrent request burst can create extra provider work near a quota boundary. A durable reservation ledger is the next step if this becomes material. Exact active constraints are never ranked away. Semantic results are a separately bounded supporting-evidence list, not an authoritative replacement for exact state.

Embeddings are pinned to `text-embedding-3-small`, explicitly requesting 1,536 dimensions. Never mix models or dimensions in an index. Changing the embedding model means a new column/table, complete re-embedding, dual-read validation, and an atomic cutover. OpenAI documents model-specific embedding output dimensions and the explicit dimensions option. [OpenAI embedding guide](https://developers.openai.com/api/docs/guides/embeddings)

During embedding-provider failure, recall still returns exact constraints with `semantic_status=unavailable`; it does not claim complete semantic recall. The active constraint ledger is capped at 32 entries and 16 KiB of values. A commit exceeding that budget fails atomically, preserving the last valid state. Recall's semantic `limit` is 1–20, default 8. This gives a predictable context packet without silently truncating non-negotiable constraints.

## Worker, deployment, and operational behavior

`python -m hivemind.worker` runs the durable worker with a separate restricted database role. It claims one job in a short committed transaction, then performs the network call outside the transaction. SQL leases last 120 seconds. Completion/failure requires the matching lease UUID, so a delayed prior worker cannot overwrite a newly claimed job. Expired running jobs can be reclaimed, retries back off, and five failed attempts enter the failed queue for investigation. Jobs are never deleted on claim. A process crash may repeat an embedding API call, but cannot lose the committed memory event.

Pool credentials are separate: `DATABASE_URL` for runtime tools; `WORKER_DATABASE_URL` for narrow job functions; `BILLING_DATABASE_URL` for the commercial control plane and optional OAuth identity binding. Migration credentials must never enter the API or worker environment. The API runs its ASGI transport lifespan together with pool cleanup. `/health/live` proves process liveness; `/health/ready` proves a bounded database round trip and, in OAuth mode, authenticated Redis write/read/delete readiness. Readiness intentionally does not make availability depend on the embedding vendor: exact-state recall still works during that vendor's outage.

The request guard validates MCP Origin headers, rejects URL tokens, enforces a 128 KiB request limit even for chunked bodies, preserves response streaming, and emits a generated request ID. Host allowlisting is configured independently. JSON logs record only route category, request ID, status, and latency. Unknown paths, Authorization headers, query strings, SQL, model content, and exception locals are excluded. Optional Sentry scrubs request objects, user data, breadcrumbs, and exception values. This protects logging by construction; operators must also disable raw proxy/body logging and keep database statement logging appropriate for secret-bearing control-plane operations.

## Verification evidence and remaining gates

Locally executed: 22 tests covering strict validation, UUID parsing, empty/duplicate/oversized batches, token shape/hash behavior, log/Sentry redaction, unavailable embedding behavior, ASGI lifespan startup/shutdown, health endpoints, bearer 401, URL-token rejection, Origin filtering, initialized Streamable HTTP, exactly two exposed tools, real tool dispatch to an injected scoped engine, structured results, tenant-parameter rejection, and chunked-body limits. These are real FastMCP/FastAPI transport tests with injected database/embedding boundaries, not a live cloud/client acceptance claim.

The dependency graph was compiled with artifact hashes and scanned using pip-audit; the scan returned no known vulnerabilities. Its machine-readable result is `docs/research/dependency-audit.json`. This is an advisory-database result, not proof of absence of vulnerabilities. Re-run the scan and native PostgreSQL integration suite in CI, build the actual image, exercise Stripe test mode and managed OAuth, test each advertised native client, and run the restore/rollback drill before selling a production SLA.
